TrustGuard 复盘：LLM 把召回拉满，F1 却几乎没动

项目：TrustGuard —— Agent 输出可信性检查器，97 个测试用例。本文记录一次真实的校准过程，以及”指标全面提升”的假象是怎么被拆穿的。

问题的起点

TrustGuard 的任务很朴素：检查 Agent 产出的内容是否存在可信性问题（虚构、未经证实的前提、越界的确定性表述……）。第一版用纯规则实现，结果是：

方案 召回率 误报率
纯规则 75% 0%
规则 + LLM（朴素接入） 100% 60%

召回从 75% 到 100%，听起来像一次巨大的成功。但把误报率摆到旁边看：F1 只从 85.7% 涨到 87.0%——等于白干。召回的每一分提升，都被误报吃回去了。

这是校准的第一课：永远不要只报召回率的提升，必须量出”朴素接入”的代价。 两个口径结论不同时，两个都要报。

逐样本归因，而不是笼统归咎

拿到 60% 误报率后，最容易得出的结论是”LLM 不行”。我们没有停在这句话，而是把每一个误报样本归因到具体的检查器维度。结果发现：

  • 误报 全部 集中在 assumption（前提假设）这一个检查器；
  • 它对召回率的贡献是 0——没有一条它独有的检出；
  • 却贡献了 全额 的误报。

一个”零召回增量 + 全额误报来源”的维度，处理方式只有一个：把它移出判定链，降级为提示项 / 标注项，而不是让它继续污染判定结果。

试 prompt 纠正，变差就如实回退

下一步是尝试用 prompt 纠正 assumption 的行为，在指令里明确写”不要把常识或定义列为缺陷”。结果在 temperature=0 下，误报反而从 6 条涨到 9 条——这是真实的恶化，不是噪声。

根因分析：这个任务没有天然的停止条件。模型对”什么算缺陷”的自我评估没有被校准，写得越具体，它反而越积极地找东西报。结论不是”prompt 没写好”，而是”这类维度不适合交给 LLM 判定”，于是回退方案，维持移出判定链的决定。

教训：纠正实验要保留”试错—回退”的记录。 变差了就退回来并写明原因，这不丢人；掩盖了才危险。

不要为好看改 ground truth

评估集里有一条样本的标签存在争议。它留着，FPR 就差 10 个百分点——诱惑很大。但我们选择保留存疑标签，并在文档中如实说明。

金标准一旦掺假，下游所有评估都失去意义。1 条存疑样本就是 1 条，”顺手改成一致的”是评估体系腐烂的开始。

最后

TrustGuard 最终的形态：规则检查器守召回的下限（0 误报），LLM 只在能证明自己净增收益的维度上参与判定。97 个测试、93 过（截至发布时的实数以仓库 README 为准），全部开源。

一句话总结这次校准：接入 LLM 不是目的，净增收益才是；量不出净增收益的组件，就应该被移出判定链。
